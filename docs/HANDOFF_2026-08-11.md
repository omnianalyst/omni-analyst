## User intent and product direction

The user wants Omni Analyst to make an extremely complicated backend feel
simple. The desired product is not a Bloomberg clone and not a page full of
technical machinery. The backend may be broad; the end-user funnel should be
narrow, ranked, legible, and candid about what was measured.

Current top-level product surface:

- **Portfolio** — the user's trading book, performance, positions, activity,
  and separately labelled external read-only wallet balances.
- **Discover** — ranked stocks/ETFs, defensive assets, crypto, sector leaders,
  search, watchlists, and alerts.
- **System** — health, coverage, calibration, loop/provider status, and
  operational truth.
- **Settings** — connections and provider/deployment state. This page is still
  more status screen than control center; completing it is a priority.

Persistent design preferences expressed by the user:

- Minimal and clean, but not empty or artificially limited.
- Rank the best measured choices within useful categories.
- Show enough candidates to compare (roughly top 10–15), not one mysterious
  winner.
- Stocks/ETFs, crypto, and defensive assets need explicit organization.
- Risk and market behavior/hedging relationships should be understandable.
- A metric must state its horizon and meaning; no unexplained percentage.
- Keep complex processing in the background and surface the highest-value
  conclusions.
- Never hide missing coverage. The Monero omission prompted the governed
  crypto census and explicit coverage audit.
- ETFs are currently the preferred portfolio core unless a point-in-time,
  costed experiment proves that a custom portfolio is better.
- External wallets must be read-only and non-custodial.
- Small convenience tools are welcome if they stay out of the way; the header
  bulletin is the example.

## Deployment caveat and current workaround

Normal Docker builds on `deployment-host` have recently failed because the host
cannot reliably resolve container registry DNS. Service containers were given
explicit public DNS in `docker-compose.prod.yml`, which fixed runtime provider
access, but the host-level image-pull/build problem may remain.

Recent deployments used an **offline local image patch**:

1. Rsync changed source/migrations/UI to `/home/user/omni-v2`.
2. Create a temporary container from the existing local image.
3. `docker cp` the source and migrations into `/app`.
4. `docker commit` it back to `omni-api:latest` or
   `omni-scheduler:latest`.
5. Recreate API/scheduler with `--no-build`.

This kept production working, but it is not the desired release system. It
does not naturally label images with the Git SHA and is easier to make
non-reproducible.

Priority operational remediation:

- Fix host-level registry DNS/pulls.
- Build normally from a tagged commit.
- Label images with the Git SHA and build timestamp.
- Preserve a rollback image before replacement.
- Back up the database before migrations.
- Add one smoke-test script covering health, migration, API routing and UI
  asset hashes.

`DEPLOY.md` describes the intended normal build and the local Neutron wheel
requirement. Note that current production also uses a shared external Caddy
container; do not assume the compose `edge` service is the active public edge.

### Shared Caddy rule

Whenever adding a new top-level API router, update both:

1. The repository `Caddyfile` matcher.
2. Both Omni matchers in `/deployments/caddy/Caddyfile` (public domain and
   Tailscale/internal site).

Validate before reload:

```bash
docker exec caddy caddy validate --config /etc/caddy/Caddyfile
docker exec caddy caddy reload --config /etc/caddy/Caddyfile
```

Back up the shared config before mutation. It also routes unrelated services.

### ETF portfolio experiment

Implemented at commit `ec9e6a0`:

- Reusable, costed ETF-versus-constituent research harness.
- Compared sector ETF, equal-weight constituents, ranked top-N and an
  ETF/ranked hybrid.
- Decision at close `t`, costs and target weights applied before return at
  `t+1`.
- Turnover, ETF spread and annual ETF expense assumptions.
- CAGR, volatility, Sharpe, drawdown, tracking error and information ratio.
- Top-5/10/15 and 5/20/50 bps sensitivity.
- Honest `current_membership_preview` label when today's constituents are
  applied backward.
- Refusal on unresolved held-price/ticker gaps rather than invented returns.

The exact report is `docs/ETF_PORTFOLIO_EXPERIMENT.md`.

Exploratory conclusion:

- Equal-weight constituent baskets beat their sector ETF CAGR in 7/9 testable
  sectors and Sharpe in 7/9, median excess CAGR +1.40%, but improved maximum
  drawdown in only 3/9.
- The price-quality top-10 ranker beat only 3/9 sectors. Median excess CAGR was
  -2.70%; a huge technology result distorted the mean.
- The 80% ETF / 20% ranked hybrid usually sacrificed a little CAGR (median
  -0.49%) but improved maximum drawdown in 8/9 sectors.
- Therefore the active stock ranker does **not** pass. ETFs remain the default
  core. The hybrid is only a risk-control research candidate.

Do not present this historical preview as an investment recommendation in the
UI. It is survivorship-biased until dated constituents and weights are owned.

## Architecture and safety boundaries

### Audience isolation and licensing

Every claim read must preserve:

```text
shared redistributable claims
+ the authenticated user's own private claims
```

Polygon and exchange-derived market data may be `byo_only`. Never expose one
user's licensed/private claims to another or make them anonymous/shared without
a real redistribution licence. Read `src/omni/coverage/visibility.py`,
`src/omni/credentials/catalog.py`, and the redistribution section of
`DEPLOY.md` before changing queries or providers.

### Point-in-time correctness

Historical experiments must use what was knowable at the decision time:

- Fundamentals join on `knowledge_date`, not merely fiscal `event_date`.
- Scores at `t` execute no earlier than the following session.
- Current membership applied backward must remain labelled exploratory.
- Missing delisting/ticker history is a refusal, not a zero return.
- Costs and turnover are explicit.
- A holdout or forward shadow period is required before capital moves.

### Trading boundary

Adapters and credentials existing does not mean trading is enabled.

- API service should not receive scheduler trading secrets.
- Hyperliquid must use an agent wallet, not a raw account wallet capable of
  withdrawal.
- Read-only is the default.
- Paper/live modes, walk-forward gates, reconciliation and risk gates must stay
  explicit.
- Never broaden live-order authority as a side effect of Settings/UI work.

### Wallet boundary

- Public addresses only.
- No seed phrases/private keys.
- No transaction request for portfolio tracking.
- No fabricated USD total when asset pricing is incomplete.
- External wallet holdings are not managed trading NAV.

### Data honesty

- A missing value is not zero.
- Provider failures should remain visible in coverage/error metadata.
- Rankings are measurements within a declared universe, not recommendations.
- Do not cache an empty provider result for an hour; scanner already avoids
  pinning empty price responses.
- Do not use Yahoo/yfinance output as ingested redistributable claims. Scanner
  uses it only for display/research under existing rules.
